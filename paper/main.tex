\begin{abstract}
We demonstrate browser-based approximate nearest neighbour (ANN) search over $35.2$ million English Wikipedia passages hosted on a static CDN. The browser embeds queries, downloads selected vector clusters using inverted file (IVF) routing, ranks their vectors, and fetches text for the top results. Visitors can inspect passages, timings, and download costs for their own questions. A companion lab measures agreement and download size across settings. On a desktop with primed CDN caches, the default settings (32k clusters, SQ6 centroids, four probes) yield an estimated $174$~ms for a $128$-token query after startup, based on separate means for embedding, vector retrieval, and ten-passage text loading. Worker startup averages $2.46$~s. At the same settings, the browser agrees with exact top-1 search on $\DefaultAgreement{}\%$ of $10{,}000$ queries generated by adding noise of magnitude $0.4$ to passage embeddings.
\end{abstract}

\section{Introduction}
Given a dataset of vectors and a query vector, $k$-nearest neighbour (kNN) retrieval finds the $k$ dataset vectors closest to the query under a chosen distance metric (Euclidean distance in our demo). Approximate nearest neighbour (ANN) search is used to speed up this task on large collections, at the cost of potentially missing some of the true nearest neighbours. In retrieval-augmented generation (RAG), ANN search is used to retrieve passages that a language model uses as context to generate an answer~\cite{lewis2020rag}.

Conventional ANN systems keep the index on the machine that runs the search, in memory or on disk~\cite{DiskANN,spann}. On the Web, this typically means running search on a server or downloading the full index to the browser, which would yield prohibitively large data transfer for our corpus. The FP16 vectors for our $35.2$ million Wikipedia passages alone occupy about $27$~GB before compression.

Our method uses an inverted file (IVF) index built with Faiss~\cite{Faiss}. The client fetches selected clusters and ranks their vectors. The demo uses free static CDN hosting, and all query-time computation runs on the client's machine.

\subsection{Related work}
This demo builds on an earlier public image-search website by the author, omitted here due to its content. The subsequent \href{https://pypi.org/project/annpack/0.1.6/}{\mbox{ANNPack} 0.1.x} also fetches selected vector clusters over the Web.

SPANN~\cite{spann} demonstrates IVF search over vectors stored on a local SSD. Our demo applies the same idea to cluster files hosted on a CDN, allowing storage beyond a single machine. Tiptoe~\cite[Section~4]{Tiptoe} uses IVF-style cluster selection and computes similarity scores under encryption on a dedicated server.

DiskANN~\cite{DiskANN} computes ANN by traversing a graph (stored on SSD). MeMemo~\cite{MeMemo} and WebANNS~\cite{WebANNS} keep graph indexes in browser RAM and IndexedDB; WebANNS evaluates up to $480{,}000$ passages. Importing our remote corpus into such local indexes would require a large initial data transfer; we avoid that import by fetching only selected clusters.

More broadly, \href{https://pagefind.app/}{Pagefind} (keyword search) and \href{https://github.com/phiresky/sql.js-httpvfs}{sql.js-httpvfs} (SQL) also process selectively downloaded static data in the browser.

\section{Demonstration scenario}
\label{sec:demo}
Both public pages use Maloyan's dataset of $35{,}167{,}920$ passages from a December 2022 snapshot of English Wikipedia~\cite{wiki-minilm}. Wikipedia gives visitors a broad choice of topics. A full index download would be prohibitively large. Our method makes browser search practical at this scale with only free static CDN hosting.

\paragraph{Wikipedia search.}
Visitors can enter any text or questions of their choice and receive ranked passages linked to Wikipedia (Figure~\ref{fig:search-demo}). Defaults are 32k clusters, SQ6 centroids, four probes, and ten results. Controls offer three cluster counts, six centroid formats, and $1$--$100$ probes. The page reports embedding, centroid-loading, retrieval and text-loading times, and vector downloads.

\paragraph{Clustering lab.}
The lab (Figure~\ref{fig:lab-demo}) offers noise presets and checks for cluster count, probes and centroid format. It reports top-1 agreement with exhaustive Faiss search. Visitors select $1$--$10{,}000$ perturbed-passage queries per configuration (default $10$). Short runs uniformly sample a shared subset. At the poster, visitors can run short checks and discuss the plots.

\section{Method outline}
Figure~\ref{fig:method} traces local computation and the static files downloaded at startup and during search. The probe count sets how many clusters the browser fetches and searches.

We use the Wikipedia passages and precomputed embeddings in Maloyan's dataset~\cite{wiki-minilm}. The \texttt{all-MiniLM-L6-v2} encoder~\cite{minilm-model-card} produces these $384$-dimensional embeddings. We chose MiniLM to balance semantic search quality, model size and inference cost. Its Xenova ONNX conversion~\cite{xenova-model-card} lets Transformers.js~\cite{transformersjs} embed queries locally in the same vector space as the stored passages. The browser uses the \texttt{q8} model and truncates inputs to $256$ tokens.


\paragraph{Index preparation.}
We train $C$ centroids with Faiss $k$-means~\cite{Faiss}, using $20$ iterations on about $2.1$ million uniformly sampled passages. We assign each passage to its nearest centroid and store its ID and FP16 vector in that centroid's gzipped file. Centroids are published in FP16 and compressed formats. Passage vectors remain FP16, occupying about $27$~GB per index layout before compression.

\paragraph{Result text.}
We group text into Brotli files of $500$ consecutive passage IDs, except for the final file, to balance privacy and download size. Larger batches make text requests less specific by covering more possible result IDs, at the cost of more unused text per download. These batches are shared across cluster counts.

\paragraph{Static hosting.}
On the \href{https://developers.cloudflare.com/pages/functions/pricing/#static-asset-requests}{Cloudflare Pages Free plan}, the $70{,}336$ text files use $71$ branch deployments. Vectors and centroids use $59$ more in a second project. Manifests map files to URLs. Our $1{,}000$-file upload batches are a packaging choice, below the provider's \href{https://developers.cloudflare.com/pages/platform/limits/}{$20{,}000$-file ceiling}.

\section{Supporting evaluation}
\label{sec:comparison}
We measure retrieval accuracy against exhaustive search. We time text retrieval separately in groups of ten passages.

\paragraph{Query setup.}
Configurations share \BenchmarkQueryCount{} uniformly sampled distinct source passages. For each sampled passage, we draw a Gaussian vector $v\in\mathbb{R}^{384}$, rescale it to noise magnitude $\|v\|_2=\alpha$, add it to the passage's unit embedding, and renormalise to obtain the query. Routing tests use $\alpha=0.4$. The lab also offers $0.05$ and $0.15$.

\paragraph{Noise scale.}
At $\alpha=0.4$, mean L2 query displacement across $1{,}000$ uniformly sampled passages was $55.5\%$ of the mean exact nearest-neighbour distance (excluding self-matches). Of the three scales tested, probe count affected top-1 agreement most at $0.4$.

\paragraph{Metric.}
\textbf{Top-1 agreement} is the fraction of queries whose first browser result has the same passage ID as the top result from an exhaustive Faiss L2 scan over the same renormalised FP16 passage vectors. For the $10{,}000$ high-noise queries, 32k/SQ6 and four probes agree on $\DefaultAgreement{}\%$, with a $95\%$ Wilson interval of $\DefaultAgreementLow{}\%$ to $\DefaultAgreementHigh{}\%$~\cite{wilson1927}.

\paragraph{Test environment.}
Experiments use Ubuntu~22.04 on an Intel Core i5-12400F PC with 32~GB RAM and a GTX 1660 SUPER GPU. GPU Faiss prepared the indexes. Browser experiments use Chromium~155; inference uses Transformers.js~4.3.1 with CPU-only WebAssembly and four threads. Separate \href{https://fast.com/}{FAST.com} checks reported about $300$~Mbit/s download; CDN throughput was uncontrolled.

\paragraph{Embedding compatibility.}
Re-embedding $1{,}000$ uniformly sampled passages with the q8 browser encoder yields mean and 5th-percentile cosine similarities of $0.9924$ and $0.9892$ to the stored vectors. These values show that the browser embeddings remain compatible despite small differences.

\paragraph{Configurations.}
FP16 probe sweeps use 2--5 probes at 8k and 2, 3, 4, 6, 8, 10 at 16k/32k. At 32k and four probes, we compare FP16 centroids with versions compressed to SQ8/SQ6/SQ4, symmetric INT8~\cite{Faiss}, and PQ4 with 4-bit codes per eight-component block~\cite{product-quantization}.

\paragraph{Hosting and timing.}
Vector and text files are prefetched to prime CDN caches. CDN residency and connections remain uncontrolled. Timed routing searches return one passage, fetch up to ten clusters in parallel and bypass browser HTTP caches. Untimed accuracy checks allow cached clusters. Table~\ref{tab:latency-table} reports agreement, timing and payload on the same timed queries.


Retrieval time includes routing, vector download, decompression, decoding and ranking; Sections~\ref{sec:text-retrieval}--\ref{sec:client-setup} report text retrieval, total query costs and startup. Centroids load once per configuration. Download and decode benchmarks use \BenchmarkCentroidSamples{} trials per file. Decode time includes gzip decompression. Tables give mean and $95$th-percentile (p95) times, and gzipped vector payload in decimal MB ($10^6$ bytes). Configuration order was randomised; the original seed and supplement order are recorded.

\subsection{Centroid loading costs}
At 32k/four probes (Table~\ref{tab:compression-table}), \textbf{SQ6 cuts centroid bytes by $61.4\%$}, from $23.24$ to $8.98$~MB. Mean loading falls from $929$~ms (FP16) to $324$~ms (SQ6), with minor effect on top-1 agreement.

\Needspace{10\baselineskip}
\subsection{Text retrieval}
\label{sec:text-retrieval}
We measure $1{,}000$ groups of ten passages, using $10{,}000$ uniformly sampled distinct passage IDs. Text retrieval takes $34.9/54.9$~ms (mean/p95), covering parallel batch downloads, Brotli decompression and text decoding. We prefetch files and bypass browser and decoded-text caches. DOM rendering is excluded.

\subsection{Total query cost}
\label{sec:client-costs}
At 32k/SQ6 and four probes, vector retrieval averages $122.4$~ms and ten-passage text loading $34.9$~ms. Embedding averages $9.1$, $16.9$ and $33.8$~ms for $64$, $128$ and $256$ tokens, giving estimated totals of $166.4$, $174.1$ and $191.1$~ms, respectively. The estimates sum the means of the three sequential stages from separate runs, excluding startup, rendering, messaging and extra ranking.

\Needspace{10\baselineskip}
\subsection{Client setup}
\label{sec:client-setup}
With the page open, startup takes $2.46/2.53$~s (mean/p95) across $100$ fresh Chromium contexts. Startup assets total about $47$~MB before HTTP compression. Separate tests measured the main downloads (size, mean time) for model weights ($23.0$~MB, $1.44$~s), WebAssembly ($14.3$~MB, $324$~ms) and 32k/SQ6 centroids ($9.0$~MB, $224$~ms). Library import, model initialization and centroid decoding averaged $371$, $642$ and $100$~ms. Some loads and components run in parallel, so startup takes less than the sum of the separate timings.

\subsection{Trade-offs and limitations}
SQ8/PQ passage codes with optional rescoring could reduce vector transfer, but their ranking quality is untested.

The timings cover controlled workloads and one live question. Latency across diverse real questions, on mobile devices and on throttled networks remains unmeasured.

\paragraph{Privacy threat model.}
The open-source client processes query text and embeddings locally. Model and runtime assets load from Hugging Face and jsDelivr. A host, CDN or network observer may link IP addresses and timing to the IDs of requested clusters and text batches. Given the requested clusters and batches, it may be possible to reconstruct the displayed result set or part of it, albeit feasibility remains an open question. Displayed results do not establish which passages were read. Co-location would avoid result-specific text requests but require one text layout per count, while selected clusters remain visible. PIR, as in Tiptoe~\cite{Tiptoe}, requires a different serving protocol.

\section{Conclusion}
Local IVF routing enables browser search over $35.2$ million statically hosted passages. The evaluation shows the trade-offs among agreement with exact search, latency, and bandwidth. Real-question quality and mobile performance remain unevaluated.
