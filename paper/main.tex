\begin{abstract}
We demonstrate browser-based approximate nearest neighbour (ANN) search over $35.2$ million English Wikipedia passages served as static Web files. The browser embeds questions locally, uses inverted file (IVF) routing to select vector clusters for parallel download, ranks their vectors, and fetches text for the top results. This avoids a full index download or an application search server. Visitors can submit questions and inspect passages, timings, and download costs; a companion lab exposes the recovery--bandwidth trade-off. At 32k clusters, SQ6 centroids, and four probes, a fixed question returning ten passages averages $130.3$~ms, including embedding and text loading, with $3.25$~MB of compressed payload. Worker startup averages $2.46$~s. At the same settings, synthetic perturbations of L2 magnitude $0.4$ yield $98.1\%$ source recovery@1; this is not real-question recall. Queries and embeddings stay local, while file requests can reveal access patterns.
\end{abstract}

\section{Introduction}
Semantic search on a static document collection usually requires a search service or a large local index. We demonstrate browser ANN over $35.2$ million passages without either: local inverted file (IVF) routing selects remote cluster files for parallel download. The probe count controls the number of clusters fetched and ranked.

Our contribution is a static-Web deployment and an interactive view of its costs, using established ANN techniques. The full FP16 vectors occupy about $27$~GB; only selected clusters and result text cross the network per query. Cloudflare Pages hosts the client and sharded index.

\subsection{Related work}
SPANN~\cite{spann} keeps centroids in memory and posting lists on disk; our browser applies this established partitioned-search pattern to static HTTP files. Tiptoe~\cite{Tiptoe} also selects semantic clusters locally but uses cryptography to hide the selected cluster from its servers. Our requests reveal access patterns. Static selective loading also appears in \href{https://pagefind.app/}{Pagefind}'s lexical search and \href{https://github.com/phiresky/sql.js-httpvfs}{sql.js-httpvfs}'s range-based database reads.

MeMemo~\cite{MeMemo} and WebANNS~\cite{WebANNS} use browser-local HNSW in RAM and IndexedDB; DiskANN~\cite{DiskANN} uses graph traversal. WebANNS evaluates up to $480{,}000$ passages. Our larger remote corpus uses parallel cluster reads; the ANN algorithm is established.

\section{Demonstration scenario}
\label{sec:demo}
The two public pages use the same Wikipedia passage collection.

\paragraph{Wikipedia search.}
Visitors enter a question or other text and receive ranked passages with links to Wikipedia articles. Defaults are 32k clusters, SQ6 centroids, four probes, and ten results. Controls offer three cluster counts, six centroid formats, and $1$--$100$ probes. The page reports embedding, centroid loading, retrieval, and text-loading times alongside vector downloads. The walkthrough compares one and four probes for the same question, inspects changed passages, and then invites audience questions. Figure~\ref{fig:search-demo} shows the actual interface. The artifact adds a bandwidth notice for large probe budgets; queries can be cancelled.

\paragraph{Clustering lab.}
Visitors vary clustering, probes, centroid format, and query noise to compare recovery, downloads, and speed. The current lab (Figure~\ref{fig:lab-demo}) fixes each configuration to $10{,}000$ queries, resolving recovery in $0.01$ percentage-point steps. Visitors compare one and four probes at 16k, then centroid formats, after inspecting noise and download costs. Precomputed vectors exclude embedding from timings.

\section{Method outline}
Figure~\ref{fig:method} traces local computation and the static files downloaded at startup and during search.

The Maloyan dataset~\cite{wiki-minilm} provides the passages and their $384$-dimensional \href{https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2}{\texttt{all-MiniLM-L6-v2}} embeddings~\cite{sentence-bert,MiniLM}.

Transformers.js~\cite{transformersjs} loads the \href{https://huggingface.co/Xenova/all-MiniLM-L6-v2}{\texttt{Xenova/all-MiniLM-L6-v2}} model in \texttt{q8} format. Queries are truncated to $256$ tokens.


\subsection*{Index preparation}
We train $C$ centroids with Faiss $k$-means~\cite{Faiss}, using $20$ iterations on about $2.1$ million uniformly sampled passages. We assign each passage to its nearest centroid and store its ID and FP16 vector in that centroid's gzipped file. Centroids are published in FP16 and compressed formats; SQ6 uses six-bit scalar quantisation per component. Passage vectors remain FP16, occupying about $27$~GB before compression.

\paragraph{Result text.}
Brotli files hold $500$ passages each, except the last. The browser fetches result batches and keeps decoded text in an $8$~MiB cache.

\paragraph{Static hosting.}
The $70{,}336$ text files use $71$ branch deployments; vectors and centroids use $59$ more in a second Pages project. Manifests map files to URLs. The uploader chooses batches of $1{,}000$ files, below the provider's \href{https://developers.cloudflare.com/pages/platform/limits/}{$20{,}000$-file Free-plan ceiling}; $1{,}000$ is our packaging choice, not that ceiling. Object storage can replace branch hosts by updating manifests and preserving CORS, content-encoding, and worker-isolation headers.

\section{Supporting evaluation}
\label{sec:comparison}
All three indexes cover $35{,}167{,}920$ passage vectors. We compare routing settings using synthetic embedding perturbations and measure the complete ten-result worker workflow with a fixed question.

\paragraph{Query setup.}
All configurations share \BenchmarkQueryCount{} queries from uniformly sampled distinct source passages. We add $v\in\mathbb{R}^{384}$ with uniformly random direction and $\|v\|_2=\alpha=0.4$ to each unit-length source vector, then renormalise. The paper reports the largest noise preset; the lab also offers $0.05$ and $0.15$.

\paragraph{Perturbation scale and scope.}
On $1{,}000$ sources, mean query-source L2 displacement is $0.378$, or $55.5\%$ of the mean nearest-neighbour distance ($0.681$) from an exact full-corpus scan excluding self matches. This controlled test exercises IVF boundary routing; isotropic passage noise does not model the question--passage distribution gap.

\paragraph{Metric.}
\textbf{Source recovery@1} is the fraction of perturbed queries whose source passage ranks first. Noise can move another passage ahead of the source even in exact search, so the plateau is not an ANN recall ceiling. Real-question recall@10 against exact search, relevance, and q8 query-encoder effects remain unevaluated. For SQ6 at four probes, the $95\%$ Wilson interval~\cite{wilson1927} is $[\DefaultRecoveryLow{},\DefaultRecoveryHigh{}]\%$ ($9{,}806/10{,}000$); intervals describe sampling uncertainty under this synthetic protocol.

\paragraph{Test environment.}
Experiments use Ubuntu~22.04 on an Intel Core i5-12400F PC with 32~GB RAM and a GTX 1660 SUPER GPU. GPU Faiss prepared the indexes. Browser experiments use Chromium~155; inference uses Transformers.js~4.3.1 with CPU-only WebAssembly and four threads. Separate \href{https://fast.com/}{FAST.com} checks reported about $300$~Mbit/s download; CDN throughput was uncontrolled.

\paragraph{Embedding compatibility.}
Re-embedding $1{,}000$ uniformly sampled passages with the q8 browser encoder yields mean and 5th-percentile cosine similarities of $0.9924$ and $0.9892$ to the stored vectors; this passage check does not validate question retrieval.

We compare $C\in\{8{,}192,16{,}384,32{,}768\}$ with 1, 4, and 8 probes. At 32k, we sweep 1, 2, 3, 4, 6, 8, and 10 probes, and compare six centroid formats at four probes: FP16, SQ8/SQ6/SQ4 and symmetric INT8~\cite{Faiss}, and PQ4 with 4-bit codes per eight-component block~\cite{product-quantization}. Cluster assignments and FP16 passage vectors stay fixed. Shared configurations run once.

\paragraph{Hosting and timing.}
Vector and text files are fetched before timing to prime the CDN cache; the fixed-question run uses $100$ preliminary searches. CDN residency and connections remain uncontrolled; cache bypass does not establish a cold CDN. Timed searches fetch up to ten clusters in parallel. Timed fetches bypass browser HTTP caching, and text loads also bypass the decoded-text cache; untimed accuracy checks allow cached cluster files.


Retrieval time covers routing, cluster download, decompression, decoding, and ranking; Section~\ref{sec:client-costs} reports startup and complete queries including embedding and text loading. Each query configuration loads its centroids once. Centroid download and decoding use \BenchmarkCentroidSamples{} trials per file. Tables report mean and 95th-percentile times (p95), and vector downloads in decimal MB ($10^6$ gzipped payload bytes). Configuration order was randomised; the original runner records its seed, and the 32k supplement records its shuffled order.

\subsection{Centroid loading costs}
Table~\ref{tab:compression-table} compares six centroid formats at 32k clusters and four probes. \textbf{SQ6 reduces mean centroid loading time from $929$~ms (FP16) to $324$~ms}, with $98.1\%$ recovery for both.

FP16, SQ8, SQ6, and INT8 differ by at most $0.09$ percentage points; these marginal intervals do not establish a quality ranking. SQ4 and PQ4 reduce recovery. The SQ4 fetch implies $\SQFourMbps{}$~Mbit/s, above the separate $300$~Mbit/s speed check: network throughput was not capped, so fetch times are observations rather than controlled bandwidth comparisons.

These results motivate 32k/SQ6 and four probes: reduced vector downloads and centroid loading costs under this synthetic protocol.

\subsection{Client setup and query costs}
\label{sec:client-costs}
\paragraph{Complete ten-result query.}
For ``How do plants turn sunlight into energy?'', the client returns ten passages at 32k/SQ6 and four probes. Across $1{,}000$ repetitions, search submission to worker reply takes $130.3/150.3$~ms (mean/p95), including embedding, vector retrieval, text loading, and message handling. Startup and DOM rendering are excluded; model and decoded centroids stay loaded. This repeated fixed-question p95 measures jitter, not variation across questions. The results require $2.48$~MB of gzipped vectors and $0.77$~MB of Brotli text ($3.25$~MB total payload, excluding HTTP headers).

\paragraph{Separate components.}
For synthetic queries, top-1 retrieval at 32k/SQ6 and four probes takes $122/187$~ms (mean/p95), with $98.1\%$ source recovery and $3.98$~MB of vectors. The fixed question transfers about $38\%$ fewer vector bytes; these component runs cannot be added to estimate varied-question end-to-end latency.
\paragraph{Startup.}
Startup spans worker creation until the model and 32k SQ6 centroids are ready, excluding page navigation. Across $100$ fresh browser contexts (reusing the Chromium process), it takes $2.46/2.53$~s (mean/p95). The model ($23.7$~MB), WebAssembly runtime ($14.3$~MB), and centroids ($9.0$~MB) total about $47$~MB. Browser caching is bypassed; loading phases overlap.

\subsection{Trade-offs and limitations}
A hypothetical $48$-byte/vector PQ index needs $1.69$~GB for codes alone. Equating this with $47+3.25Q$~MB gives about $505$ queries, or $413$ using $3.98$~MB of vectors/query before text. This illustrates byte budgets, not equal-quality or latency baselines: IDs, codebooks, caching, and storage overhead change the crossing. One million uncached fixed-question searches transfer $3.25$~TB before startup or headers. A server returns text alone but receives the query and needs search compute; that baseline is unmeasured.

FP16 passage vectors dominate transfer. SQ8/PQ passage codes with optional rescoring could reduce it, but change ranking and require evaluation. At 32k, manifest cluster sizes have median $1{,}023$, p95 $2{,}188$, and maximum $8{,}263$ passages. The four largest gzip files sum to $19.32$~MB, an upper bound at four probes, not an observed query percentile; byte tails remain unmeasured. Varied real-question end-to-end mean/p95/max, cold-connection and cold-CDN trials, and throttled/mobile profiles remain necessary before generalising the desktop timings.

\paragraph{Privacy threat model.}
Assuming the served client code is trusted, query text and embeddings stay in the browser. The host/CDN can associate IP addresses and timing with four cluster IDs among $32{,}768$, revealing semantic regions, and result-batch IDs, each identifying a set of at most $500$ passages. These requests are not cryptographically private and can reveal likely results, though not which displayed result was read. Larger batches or decoy requests add bandwidth without guaranteeing privacy; PIR, as in Tiptoe~\cite{Tiptoe}, requires a different serving protocol. We do not measure inference success from these observations.

\section{Conclusion}
Local IVF routing enables browser search over $35.2$ million passages through selective downloads from static hosting. The search page and lab expose how clustering, probing, and centroid compression affect source recovery, latency, and bandwidth.
